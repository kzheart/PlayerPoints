## 实现与边界

PG 使用 Hikari 连接池及专用有界工作线程。`PgPointsRepository` 在事务内检查真实余额、锁账户、更新余额/revision、写流水并提交；不足拒绝，溢出回滚。并发创建只获得一次起始余额。转账按 UUID 顺序锁双方，两份余额与两条流水同时提交。全库批量加减也按排序行锁处理，负数按原 bulk 语义钳零，任一账户溢出整批回滚。

API 新增 `changePointsAsync`、`payAsync`、`lookAsync`，写 Future 成功代表已提交。点券事件留在 Bukkit 主线程，JDBC 运行在工作线程。原同步 API 兼容保留，旧插件调用仍可能等待 PG；显示余额是缓存，每秒刷新在线账户，缓存不能决定是否允许扣款。`lookAsync` 提供已提交读取。MulanShop 依次等待 PG 金币、点券提交，后续扣费或离线失败时逆序等待退款。

PG 的旧批量导入、legacy 表导入、账户删除要求停服维护，避免覆盖正在进行的跨服交易。转账事件可按上游语义分别改写收/付金额；本次无改写的转账守恒测试不能覆盖所有其他插件行为。商城专用扣费拒绝金额改写，保持报价与退款金额一致。

## 真实钱包并发

两个原 Minecraft 进程在同一物理服务器上运行，以下直接调用其实际 PlayerPoints API，再核对 PG，而不是把 JDBC 连接当作游戏子服。

| 场景 | 实际结果 |
| --- | --- |
| 两服同账户，各 50 次扣 10，初值 10 | 总 100 次扣款恰 1 次成功，余额 0 |
| 两服各 50 对 +10/-5，初值 100 | 200 个操作成功，最终 600 |
| 两服对同两账户进行 200 次相反转账 | 全成功，两账户各 1000，总量守恒 |

零金额充值也参与原子请求，上述第一个场景还接受了 100 个零充值；记录 `accepted=101` 不代表成功扣款 101 次。所有节点响应和 PG 账务保存于 `live-wallet-tests.json`。

## 商城压力与跨服

| 场景 | 购买成功 | 延迟 P95 | TPS 采样最低 |
| --- | ---: | ---: | --- |
| Spawn 20 人、四货币、每人约 2 秒一单、180 秒 | 1802 | 351.05 ms | Spawn 20 |
| Spawn/Lobby 各 10 人、PG 金币+点券、180 秒 | 1802 | 349.68 ms | 两服均 20 |

两轮均无客户端超时/断线。纠正后的双服结果由后台审计证明各 10 名玩家，奖励分别来自 Spawn 901 单、Lobby 901 单。采样每轮每服 12 次；实际双服 10 秒 tick 中位数 Spawn [0.9, 1.1] ms、Lobby [0.8, 1.3] ms，两服窗口 P95 最大均 8.1 ms。这里没有复测 100 人 PG 点券负载，前一份 100 人报告使用的是每服 SQLite 点券，不能移植容量结论。

测试脚本原自动 `/server spawn` 回退会干扰主动切服。首次标为 `pg_cross_10plus10_180s` 的 1802 单实际主要在 Spawn，不计作真实双服压力结果，但其账务保留在总对账中。修正操作后通过服务端在线审计、真实奖励节点与玩家集合重新验证 `pg_real_cross_10plus10_180s`，未用脚本猜测的节点字段作结论。

纠正后的实际双服进一步覆盖：20 人各发 8 次确认恰 20 单；全服限购 5 件和全服每日 5 件各恰好 5 成功、15 拒绝；20 人注入后续货币失败全部 FAILED，已扣金币、点券退回，无奖励。前面阶段也验证个人/个人每日限购。实际 GUI 验证 Spawn 购买后切 Lobby 个人限购隐藏、两节点购买、64 数量按价扣款；PG 点券人为设为 0 时，金币先扣后完整退回，再把专用测试点券恢复到原审核值。Lobby 原版等级为 0 的不足拒绝被记录，跨服商品使用共享 PG 两币继续验证。

JFR 120 秒采样：主线程 SQLite 查询样本 0、PG 查询样本 0；批量玩家保存 802 次文件写，累计 2523.66 ms，最大单次 105.14 ms。没有采到主线程 SQL 不等于所有旧同步 API/冷读取都异步，玩家文件保存仍在主线程。
