## 旧行为与新行为

旧版每 20 tick 遍历在线玩家，各自排队执行一次建账户 UPSERT 和一次余额 SELECT。读取与交易共用一个单线程队列，即使异步也会增加扣款排队。

新版分工：

- `DataManager` 负责后端与玩家生命周期，预登录加载账户，join/quit 只传 UUID 给同步管理器。
- `PgPointsRepository` 负责事务、流水与 schema 迁移。现存账户显式读取只 SELECT，缺失时才建账户；批量校准只 SELECT，绝不开户或写余额。
- `PgPointsWallet` 保留交易 FIFO 单线程/10000 队列以兼容同节点提交顺序；另外提供读线程/256 队列，两类任务互不排队。并发同账户显式读取复用同一个未完成 Future，读取完成后移除再触发回调。
- `PgPointsSyncManager` 负责通知合并、在线账户集合、默认 30 秒兜底与诊断。通知不是扣款依据；余额检查仍在数据库行锁事务内。
- `PgPointsNotifications` 用一个独立物理连接 LISTEN，不占 Hikari 交易池，阻塞等待网络通知，不逐人查余额。30 秒左右执行 SELECT 1 检测闲置半开连接。

余额、revision、流水提交后，本服立刻发布新缓存。数据库触发器在同一事务发出 `UUID:revision` 失效通知，不发送余额。远端合并最多 100 ms 后按最多 256 UUID/批读取事实源；收到已缓存版本或旧版本的通知直接忽略，避免本服通知回送产生重复查询。批量查询结果按 revision 发布，迟到快照不能覆盖新提交。

空闲的 1000 个在线账户在同一节点上，默认每 30 秒校准 4 条余额 SELECT；实际拆分多节点时应按各节点 `ceil(人数/256)` 相加。此数字只描述余额校准，不包含开户、业务交易、用户名更新、心跳或活跃通知引起的读批次。它不是 1000 名真实游戏玩家的容量结论。

## 丢通知、故障与关闭

监听断开按 1 至 30 秒退避重连；先提交 LISTEN，再校准在线账户，避免先读后订阅的空窗。通知不是持久消息队列，断线期间可以丢失；30 秒只读批量校准补齐遗漏。数据库故障或队列拥堵时会延后，不承诺所有情况下 30 秒以内恢复。读批次请求合并，失败不重放扣款；未知交易结果仍需核查。

关闭先停止同步计时器/监听，再停止接收钱包任务，有限等待已接收的读写任务，最后关闭池。读写队列拒绝的新请求都会结束 Future，不把 JDBC 扔回调用线程执行。

离线账户 `look` 仍是缓存视图，强制读已提交余额应使用 `lookAsync`。旧同步 API 和 `look` 冷缓存仍可能等待 I/O；本次没有把所有上游命令改成异步。交易工作线程仍为每节点一个，扩大交易并行度属于后续独立负载验证，不能把本次刷新优化宣称成千人交易容量证明。

## schema 与诊断

schema 1 → 2 在事务及初始化锁内增加版本递增、提交后通知触发器，保留余额与流水；外部 SQL 更新也递增 revision 并通知。在线删账户/重建账户不受支持，仍需停服维护。旧 mulan.2 不接受 schema 2，回滚需要停服移除新增触发器、还原 schema 标记并保留当前账务，不能盲目覆盖旧备份余额。

`postgresql-settings.reconcile-interval-seconds` 默认 30，范围 5-3600；池最小 2，默认 3，监听额外占 1 个物理连接。参数修改后重启。`/points syncstatus` 为默认管理员权限的只读诊断，显示订阅/通知/读批次和队列积压，没有 SQL 或密钥输出。
