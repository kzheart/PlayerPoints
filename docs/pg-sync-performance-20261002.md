# 点券同步重设计前后性能对比 · 2026-10-02

后续状态：本文基准完成后，用户授权部署，新版已在真实两服完成升级和客户端验收，见[部署报告](pg-sync-deployment-20261002.md)。本文数据仍只代表部署前的隔离钱包 A/B 基准。

已在木兰服务器的 PostgreSQL 服务上完成旧版 `3.3.5-mulan.2` 与新版 `3.3.5-mulan.3` 的钱包链路 A/B 基准。空闲维护负担显著减少，持续交易的入队至提交 P95 延迟下降约 **91.3%**，跨节点缓存可见 P95 延迟下降约 **89.7%**；突发交易 P95 仅下降约 **6.9%**。

这是实际钱包 JAR、真实 PG、两份独立钱包和连接池的测试；两份钱包在同一个独立 JVM 内，模拟各 500 个在线账户。没有启动 Minecraft 客户端或新版游戏服，没有测 Bukkit 主线程、GUI、其他插件事件及 TPS，不能据此声称已经验证千人游戏服容量。

本轮没有修改业务实现，也没有部署或重启正式 Spawn/Lobby。测试结束后，两服仍运行 mulan.2，正式 schema 仍为 1。

## 结果

每个场景按旧、新、新、旧执行，各版本重复两轮。以下范围是两轮各自结果；百分比用两轮指标的中位值计算，不是把全部延迟样本合并后的 P95。P95 表示 95% 的该轮请求在此时间内完成。

| 场景及指标 | 旧版 mulan.2 | 新版 mulan.3 | 变化 |
| --- | ---: | ---: | ---: |
| 1000 账户空闲 65 秒：维护 SQL，含心跳 | 132,000 | 12（8 条余额批查 + 4 条心跳） | 减少 99.991% |
| 持续 100 更新/秒：交易 P95 | 24.69–28.79 ms | 2.321–2.334 ms | 下降 91.3% |
| 持续 100 更新/秒：另一节点缓存可见 P95 | 957.89–958.53 ms | 98.31–98.39 ms | 下降 89.7% |
| 持续负载：维护 SQL，含心跳、尾部排空 | 134,000 | 1,313–1,314 | 减少约 99.0% |
| 突发 1000 更新：交易 P95，5 次突发的整轮分布 | 920.12–932.53 ms | 861.72–862.32 ms | 下降 6.9% |
| 突发场景：整轮维护 SQL，含心跳 | 10,000 | 84–88 | 减少 99.14% |

持续负载每轮接收 6,502 笔更新；突发每轮接收 5,000 笔。正式 12 轮合计 **46,008 笔**，全部成功：逐账户实际余额与初值加已接受增减一致，流水数量与已接受交易一致；拒绝、写错误、刷新错误、余额差额、未完成缓存观察均为 0。预热交易和两轮烟雾测试不计入该总数。

这证明上述负载的最终账务和跨钱包缓存观察通过，不是所有故障下数据一致性的保证。通知断线、回滚、溢出等单独的 22 项回归见[同步重设计报告](pg-sync-redesign-20261002.md)；本轮没有强杀、断电、网络分区或商城跨插件补偿测试。

## 环境与方法

- 同一个木兰 PG 服务：PostgreSQL 15.19 / Debian，回环连接；运行 Temurin Java 25.0.4.1。
- 每轮单独启动 JVM，固定 `-Xms256m -Xmx768m`，双方使用相同 Guava、failureaccess、SLF4J 依赖与插桩。
- 隔离数据库及角色 `pp_wallet_ab_20261002`；每轮独立表前缀。创建 1000 个账户，每个初始余额 10000；不连接正式账务库。
- 两份独立钱包、各自 Hikari 池最大 3 / 最小空闲 1，分别持有 500 个在线 UUID。新版另有两个独立 LISTEN 连接，不占用交易池。
- 直接调用实际 Shadow JAR 的钱包 API。旧版模拟正常 20 TPS 下每秒逐个在线账户刷新，读取与交易共用工作线程；新版使用实际同步管理器，100 ms 通知合并与默认 30 秒批量校准。
- 初始化、账户缓存加载、400 笔净额为零的预热交易及 2.5 秒等待均排除在计数窗口之外。每轮最后排空任务并对照数据库余额和流水。
- 空闲场景测量 65 秒。持续场景每 20 ms 向两钱包各提交一笔，合计 100 笔/秒，所有更新都指向另一节点的在线账户；65 秒发请求后保持同步至最后观察完成，再排空。边界 tick 导致每轮 6502 笔。
- 持续场景同账户变更相隔约 10 秒，按 sweep 交替 +1/-1；每 5 ms 检查另一钱包的实际缓存是否达到提交后的期望余额。显示延迟从写 Future 完成时计算，包含观察分辨率。不要把此余额判等方法直接用于同账户快速反复回到相同余额的负载。
- 突发场景每轮包含五次：先触发两节点全体显示刷新/校准，立即提交合计 1000 笔更新，排空并等待 500 ms，再进入下一次。突发只对照写延迟和最终 PG 账务，没有测跨节点可见延迟。
- 交易延迟从入队到写 Future 完成，包含排队及数据库提交；不是单条 SQL 的执行时间。
- JDBC 代理对实际 execute 调用计数。不含 COMMIT 或触发器内部语句。维护 SQL 包含旧刷新开户 UPSERT、显示 SELECT、监听心跳；每笔正常交易的 4 条客户端 SQL 在两版均保留，不算维护 SQL。
- 停止发请求后仍统计尾部同步/排空，因此持续场景旧版整窗 66.100–66.108 秒、新版 65.088–65.106 秒。不能把 SQL 总数解释为完全相同整窗时长下的 QPS。

## 资源代价与剩余瓶颈

本基准测得的 JVM CPU 时间如下；包括采样、反射和 SQL 计数代理开销，不代表 PG 服务端 CPU 或 Minecraft 总 CPU。

| 场景 | 旧版 JVM CPU 秒 | 新版 JVM CPU 秒 |
| --- | ---: | ---: |
| 空闲 | 3.87–3.91 | 0.69–0.83 |
| 持续交易 | 5.60–5.62 | 4.32–4.41 |
| 突发 | 2.11–2.13 | 2.19–2.25 |

新版有独立监听、读取线程和通知处理开销，突发场景 CPU 没有下降。测量窗口采样到的两节点总物理连接峰值：旧版空闲/持续为 4，突发为 2–3；新版各场景为 6–7（包括两个监听连接）。双方池配置相同，但实际增长不同；因此这些收益不是以完全相同连接占用取得的。每 5 ms 采样也可能漏掉更短的峰值。

突发写入仍在每节点一个 FIFO 工作线程内逐笔事务提交。刷新队列干扰消除后，写事务本身占主要时间，这解释了只有约 7% 的突发改善。扩大交易并行度、账户分片、批次提交需要单独设计顺序、回滚与跨节点一致性规则，并重新测试；本轮没有实施这些改动。

同服务上的其他进程可能影响结果，两次重复只提供当前硬件及负载的初步对照，不是统计置信区间。没有 MySQL 对照，也没有递增到饱和的最大吞吐测试。
