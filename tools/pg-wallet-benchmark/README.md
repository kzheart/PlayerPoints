# PG 钱包前后对比基准

`WalletBenchmark.java` 直接加载待比较版本的实际 Shadow JAR，使用真实 PG、两份独立连接池与钱包实例。模拟两节点各 500 个在线 UUID；不启动 Bukkit，不触发其他插件事件，不测游戏 TPS、GUI 或极限容量。

2026-10-02 的完整数据和边界见 `../../docs/pg-sync-performance-20261002.md`。每次应使用独立 PG 测试库和角色，不能连接正式账务库；每个场景使用独立表前缀。程序会创建 1000 个账户、余额 10000，并记录测试流水。运行结束后需要删除整个测试库/角色。

编译 classpath 包括待测新版 JAR（含重定位的 Hikari/PG 驱动），运行另需 Guava、failureaccess、SLF4J API。基准兼容 Java 8 字节码，本轮运行 Java 25。新旧版本分别使用独立 JVM，保持 `-Xms256m -Xmx768m`、PG 配置、JDBC 池上限 3/节点和账户初值一致。

环境变量：`PLAYERPOINTS_TEST_PG_URL`、`PLAYERPOINTS_TEST_PG_USER`、`PLAYERPOINTS_TEST_PG_PASSWORD`，不要写入源码、命令参数或报告。

程序参数：`old|new idle|mixed|burst <唯一表前缀> <时长秒数> <结果JSON路径>`。前缀符合仓库验证规则且长度不超过 41；混合负载固定为两节点各 50 次更新/秒，所有更新指向另一节点的在线账户。burst 忽略时长，执行 5 轮，每轮显示校准开始后立即提交 1000 次更新。

每次先初始化并预热，计数窗口排除这些工作。SQL 计数由同一 JDBC 代理记录实际 execute 调用，不把 COMMIT 或触发器内部语句计入客户端 SQL 次数。交易延迟从入队到 Future 完成，显示同步延迟从提交 Future 完成到另一钱包缓存达到该值，后者按 5 ms 检查，包含检查分辨率。当前负载同账户两次更新相隔 10 秒，短于该间隔的显示延迟可以用余额观测；不要直接把该测量方式移植到更高频、反复变回同一余额的工作负载。

持续负载停止后保留同步至最后观察值到达，再停止任务和监听，排空读写队列，对照全部 1000 个账户与流水数量。出现错误、拒绝、账户差额或遗留显示观察时返回非零。

按 old-new-new-old 运行每种场景两轮以降低次序偏差。一次基准仍不足以推断所有硬件和网络条件的性能，极限吞吐需要另设计递增负载测试。JVM CPU 秒包括采样/SQL 计数开销，不是 PG 服务端 CPU；新版本独立监听与读队列会增加连接和线程资源。
